**Дата анализа:** 3 октября 2025

## Обзор

Проведен комплексный анализ модели `StockSnapshot` для оценки возможности её полного удаления и замены на динамическую агрегацию данных из первичных транзакций (`PurchaseItem` и `WriteOff`).

## 1. Текущая архитектура StockSnapshot

### 1.1 Назначение модели
`StockSnapshot` реализует **Unified Ledger Model v1.0** - центральный журнал движений материалов, который:
- Учитывает все приходы и расходы материалов
- Связывает транзакции с их источниками (`source_type`, `source_id`)
- Обеспечивает консистентность данных через сигналы
- Предоставляет единую точку для расчета остатков

### 1.2 Структура модели
```python
class StockSnapshot(models.Model):
    date = models.DateField()                    # Дата движения
    object = models.ForeignKey(Object)          # Объект
    material = models.ForeignKey(Material)      # Материал
    unit = models.ForeignKey(Unit)              # Единица измерения
    quantity_signed = models.DecimalField()     # Количество с знаком (+/-)
    stage = models.CharField()                  # Этап работ
    source_type = models.CharField()            # Тип источника
    source_id = models.PositiveIntegerField()   # ID источника
    responsible = models.ForeignKey(User)       # Ответственный
    comment = models.TextField()                # Комментарий
    is_archived = models.BooleanField()         # Архивный флаг
```

## 3. Оценка возможности удаления

### 3.1 ✅ **ПОЛОЖИТЕЛЬНЫЕ АСПЕКТЫ**

#### Упрощение архитектуры:
- Устранение дублирования данных
- Единая точка истины в первичных транзакциях
- Автоматическая консистентность данных

#### Производительность:
- Меньше записей в БД
- Упрощенные запросы
- Отсутствие необходимости синхронизации

#### Поддерживаемость:
- Меньше кода для поддержки
- Упрощенная логика
- Меньше точек отказа

### 3.2 ❌ **ОТРИЦАТЕЛЬНЫЕ АСПЕКТЫ**

#### Сложность реализации:
- Требуется переписать всю логику расчета остатков
- Необходимо обновить все API endpoints
- Сложная миграция данных

#### Производительность запросов:
- Агрегация на лету может быть медленнее
- Сложные JOIN запросы
- Необходимость кэширования

#### Функциональность:
- Потеря истории изменений остатков
- Сложность реализации архивации
- Проблемы с валидацией остатков

## 4. Альтернативные подходы

### 4.1 Гибридный подход
Сохранить `StockSnapshot` как **только для ручных корректировок**:
- Автоматические записи из `PurchaseItem`/`WriteOff` - удалить
- Ручные корректировки остатков - оставить
- Расчет остатков - через агрегацию

### 4.2 Полная замена
Удалить `StockSnapshot` полностью:
- Все остатки рассчитывать через агрегацию
- Ручные корректировки через `WriteOff` с типом "correction"
- Архивирование через `ArchivePeriod` без привязки к `StockSnapshot`

### 4.3 Оптимизация текущей модели
Улучшить существующую модель:
- Добавить кэширование
- Оптимизировать индексы
- Упростить сигналы

## 5. Рекомендации

### 5.1 **НЕ РЕКОМЕНДУЕТСЯ** полное удаление `StockSnapshot`

#### Причины:
1. **Сложность миграции** - потребуется переписать значительную часть кода
2. **Потеря функциональности** - история изменений, архивация, валидация
3. **Производительность** - агрегация на лету может быть медленнее
4. **Риски** - высокая вероятность ошибок при миграции

### 5.2 **РЕКОМЕНДУЕТСЯ** гибридный подход

#### Этапы реализации:
1. **Фаза 1**: Удалить автоматические записи из сигналов
2. **Фаза 2**: Оставить только ручные корректировки
3. **Фаза 3**: Обновить расчет остатков через агрегацию
4. **Фаза 4**: Оптимизировать производительность

#### Преимущества:
- Сохранение функциональности
- Упрощение архитектуры
- Постепенная миграция
- Минимальные риски
